# R7-REM-004: CI starvation guard and tiered candidate verification (Conditor)

Source: Indy-init `docs/rehearsal-007/REMEDIATION-PLAN.md`, work package R7-REM-004, from Rehearsal 6's CI starvation (Indy-init `docs/REHEARSAL-006-RESULTS.md`, "CI starvation, 22:22–23:54").

## What happened

Measured from the GitHub API for indy-init-rehearsal-006, 2026-10-28 20:00 to 2026-10-29 03:00 UTC:

- 427 workflow runs. Of the 123 main Build-and-test runs, 111 were cancelled, 11 failed and only 1 succeeded (the kickoff).
- Main runs open at once grew to about 40. About 104–126 jobs waited for a runner while 4–19 ran.
- No main result arrived for 124 minutes. Cancelled jobs used about 1,297 runner-minutes.
- The causes:
  - **A per-commit concurrency group on main** (`…-${{ github.sha }}`, `cancel-in-progress: false`), introduced at 22:22 by an agent editing a pipeline imported from Rehearsal 5. This was the root cause, and it is still present in Rehearsal 6's final workflow.
  - **Job-level `if: always()`**, so cancelled runs started their jobs anyway.
  - **Job-level shared groups** that cancelled older candidates' pending jobs.
  - **Validation workflows on every push to every branch plus pull requests**, which ran each pull-request push twice and added 288 runs.

Conditor's `fsharp-limen-web` build workflow was already safe: one group per ref, superseded runs cancelled, and a timeout. The rehearsal replaced it, and nothing checked the replacement.

## Requirements

1. **`conditor ci-policy check`.** A deterministic check of a repository's `.github/workflows/*.yml` that fails closed:
   - **CIP-001:** no per-commit concurrency group in a push or pull-request workflow, at workflow or job level.
   - **CIP-002:** every push or pull-request workflow has a workflow-level concurrency group.
   - **CIP-003:** pull-request workflows cancel superseded runs.
   - **CIP-004:** no job-level `always()`; use `!cancelled()`.
   - **CIP-005:** every job that runs steps has `timeout-minutes`.
   - **CIP-006:** no unfiltered `push` combined with `pull_request`.
   - **CIP-007:** a candidate workflow is dispatch-only, keyed on its candidate input, and never cancels in progress.
   - **CIP-000:** a workflow the check cannot read is a finding, never a pass.
2. **Templates.**
   - The foundations workflow gets a per-ref concurrency group and runs on push to `main` only, plus pull requests.
   - A new tier-3 `candidate-acceptance.yml` verifies one pinned SHA on `main`:
     - it is dispatch-only and keyed on the candidate;
     - it is never cancelled by development pushes or by another candidate.
3. **Guard tests.**
   - Every workflow Conditor scaffolds passes the policy.
   - Rehearsal 6's actual workflows fail it, with the rules above.
